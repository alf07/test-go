# Wallet API

REST API для работы с балансами кошельков. Я разработал проект на Go и PostgreSQL в рамках тестового задания на Junior Go-разработчика.

## Возможности

- Получение баланса кошелька по UUID.
- Пополнение (`DEPOSIT`) и снятие (`WITHDRAW`) средств.
- Проверка достаточности средств перед снятием.
- Сохранение успешных операций в таблице `history`.
- Изменение баланса и запись истории в одной транзакции PostgreSQL.
- Обработка конкурентных операций с одним кошельком.
- Интеграционные тесты для API, репозитория и конкурентных сценариев.

## Стек

- Go
- PostgreSQL
- `database/sql` и драйвер `pgx`
- `godotenv` для загрузки `config.env`
- Docker Compose для запуска приложения и PostgreSQL

## Структура проекта

```text
.
├── main.go
├── config.env.example
├── db/
│   ├── connection.go
│   ├── schema.sql
│   └── seed.sql
├── dbmodel/       # SQL-запросы
├── repository/    # Выполнение SQL и транзакции
├── services/      # Бизнес-логика и валидация
├── handler/       # HTTP-обработчики
├── tests/         # Интеграционные тесты
├── Dockerfile
└── docker-compose.yml
```

Пакет `db` отвечает за подключение к PostgreSQL. В `dbmodel` я храню SQL-запросы, `repository` выполняет их и управляет транзакциями, `services` содержит бизнес-логику, а `handler` обрабатывает HTTP-запросы и формирует ответы. `main.go` связывает компоненты и запускает HTTP-сервер.

## Конфигурация

При локальном запуске приложение читает `DATABASE_URL` из файла `config.env`. Создай этот файл в корне проекта:

```dotenv
DATABASE_URL=postgres://postgres:YOUR_PASSWORD@localhost:5432/testgo?sslmode=disable
```

Замени имя пользователя, пароль и имя базы на свои значения. Я добавил `config.env` в `.gitignore`, чтобы не публиковать секреты. Для примера конфигурации используется `config.env.example` без реальных паролей.

## Локальный запуск

1. Запусти локальную PostgreSQL.
2. Создай базу данных, например `testgo`.
3. Создай таблицы по схеме из `db/schema.sql` или используй уже созданную схему.
4. При необходимости заполни таблицу `wallet` тестовыми данными из `db/seed.sql`.
5. Создай и заполни `config.env`.
6. Из корня проекта выполни:

```bash
go mod download
go run .
```

HTTP-сервер слушает порт `8081`.

## REST API

### Получить баланс

```http
GET /api/v1/wallets/{WALLET_UUID}
```

Пример:

```bash
curl -i http://localhost:8081/api/v1/wallets/11111111-1111-4111-8111-111111111111
```

В текущей реализации успешный ответ содержит баланс в виде JSON-числа, например:

```json
1000
```

### Выполнить операцию

```http
POST /api/v1/wallet
Content-Type: application/json
```

Пример пополнения:

```json
{
  "walletId": "11111111-1111-4111-8111-111111111111",
  "operationType": "DEPOSIT",
  "amount": 100
}
```

Пример запроса через `curl`:

```bash
curl -i -X POST http://localhost:8081/api/v1/wallet \
  -H 'Content-Type: application/json' \
  -d '{"walletId":"11111111-1111-4111-8111-111111111111","operationType":"DEPOSIT","amount":100}'
```

Допустимые значения `operationType`: `DEPOSIT` и `WITHDRAW`. В исходном описании задания написано `valletId`; я трактовал это как опечатку и использовал поле `walletId`.

Сейчас API принимает сумму в целых единицах валюты. Хотя столбец PostgreSQL имеет тип `numeric(18,2)`, дробные значения через текущий DTO не поддерживаются.

### HTTP-статусы

| Код | Значение |
|---|---|
| `200 OK` | Операция выполнена успешно |
| `400 Bad Request` | Некорректный JSON, UUID, сумма или тип операции |
| `404 Not Found` | Кошелёк не найден |
| `409 Conflict` | Недостаточно средств для снятия |
| `405 Method Not Allowed` | Использован неподдерживаемый HTTP-метод |
| `500 Internal Server Error` | Внутренняя ошибка приложения или базы данных |

## Почему я оставил POST, хотя рассматривал PATCH

В техническом задании явно указан `POST /api/v1/wallet`, поэтому я сохранил заданный контракт.

Если бы я проектировал API самостоятельно, я бы рассмотрел `PATCH /api/v1/wallets/{WALLET_UUID}`: мы не создаём новый кошелёк, а изменяем баланс существующего. Пополнение увеличивает текущий баланс на указанную сумму, а снятие уменьшает его при условии достаточного остатка.

Запись операций в таблицу `history` — моё дополнение к ТЗ. Я добавил её, чтобы сохранять информацию об успешных операциях и фиксировать изменение баланса вместе с записью истории в одной транзакции. Само наличие истории не является причиной выбирать `POST` вместо `PATCH`.

Таким образом, в этой версии я использую `POST` для соответствия ТЗ. При самостоятельном проектировании API я бы отдельно рассмотрел `PATCH` как вариант для изменения существующего ресурса.

## Конкурентность и транзакции

Баланс меняется атомарными SQL-запросами в PostgreSQL. Запрос снятия содержит условие `balance >= amount`, чтобы конкурентные операции не могли увести баланс в минус.

Изменение баланса и вставка записи в `history` выполняются в одной транзакции. Если запись истории завершается ошибкой, транзакция не должна фиксировать изменение баланса. Для синхронизации конкурентных обновлений одной строки я использую механизмы блокировок PostgreSQL; отдельный Go `sync.Mutex` не добавлял.

## Тестирование

Я запускал интеграционные тесты на своей локальной PostgreSQL. Они проверяют получение баланса, пополнение, снятие, отсутствие кошелька, недостаточный баланс, HTTP-ошибки и конкурентные операции. Тесты создают кошельки с отдельными UUID и очищают созданные данные после выполнения.

Запустить все тесты:

```bash
go test ./... -count=1
```

Проверить гонки данных в Go:

```bash
go test -race ./tests -count=1
```

Посмотреть покрытие основных пакетов:

```bash
go test \
  -coverpkg=./handler,./services,./repository,./dbmodel \
  -coverprofile=coverage.out \
  ./tests -count=1

go tool cover -func=coverage.out
```

Во время разработки я получил покрытие **88,5% операторов** в пакетах `handler`, `services`, `repository` и `dbmodel`.

**Использование ИИ:** интеграционные тесты я сгенерировал с помощью ИИ. Затем я запускал их на своей локальной PostgreSQL и проверял результаты. Команды `go test ./... -count=1`, `go test -race ./tests -count=1` и проверка `go vet ./...` завершились успешно.

## Нагрузочное тестирование

Я запускал нагрузку на локальный HTTP-сервер с помощью утилиты [`hey`](https://github.com/rakyll/hey). Запросы `POST` выполняли пополнение одного и того же кошелька.

Зафиксированный успешный прогон:

- длительность: `10.0841` секунды;
- пропускная способность: `1090.53 RPS`;
- успешные ответы: `10997` со статусом `200`;
- ответы `5xx`: `0`;
- среднее время ответа: около `45.4 ms`;
- p50: `45.9 ms`;
- p99: `86.3 ms`.

После прогона я проверил данные в PostgreSQL: баланс составил `10997.00`, в истории было `10997` успешных пополнений, а их суммарная величина составила `10997.00`. В этом запуске баланс и история совпали с числом успешных операций.

Это результат короткого теста на моей локальной машине. Он не гарантирует такую же производительность на другом оборудовании и не заменяет длительное нагрузочное тестирование с мониторингом ресурсов.

## Запуск через Docker Compose

Для этого способа запуска локально устанавливать Go и PostgreSQL не требуется: Docker Compose собирает контейнер приложения и запускает отдельный контейнер PostgreSQL. Нужны установленный и запущенный Docker Engine и команда `docker compose`.

Проверь установку:

```bash
docker --version
docker compose version
```

### 1. Подготовь конфигурацию

В корне проекта создай `config.env` на основе `config.env.example`. Для контейнерного запуска в нём должны быть заданы параметры PostgreSQL и URL, по которому приложение подключается к базе внутри Docker-сети:

```dotenv
POSTGRES_USER=wallet_user
POSTGRES_PASSWORD=wallet_pass_123
POSTGRES_DB=testgo
DATABASE_URL_DOCKER=postgres://wallet_user:wallet_pass_123@postgres:5432/testgo?sslmode=disable
```

Если в `config.env` уже есть `DATABASE_URL` для локального PostgreSQL, оставь его для локального запуска. В Compose используется отдельная переменная `DATABASE_URL_DOCKER`, потому что внутри контейнера `localhost` указывает на сам контейнер приложения, а сервис PostgreSQL доступен по имени `postgres`.

Не публикуй `config.env` в Git: файл должен быть указан в `.gitignore`.

### 2. Собери и запусти контейнеры

Из корня проекта выполни:

```bash
docker compose --env-file config.env up --build -d
```

Команда собирает образ приложения, запускает PostgreSQL и приложение в фоне. В `docker-compose.yml` приложение ожидает, пока проверка готовности PostgreSQL не станет успешной.

Посмотри состояние контейнеров:

```bash
docker compose ps
```

Посмотри логи приложения и базы:

```bash
docker compose logs app
docker compose logs postgres
```

### 3. Проверь API

После запуска запроси баланс одного из тестовых кошельков, добавленных через `db/seed.sql`:

```bash
curl -i http://localhost:8081/api/v1/wallets/11111111-1111-4111-8111-111111111111
```

Проверь пополнение:

```bash
curl -i -X POST http://localhost:8081/api/v1/wallet \
  -H 'Content-Type: application/json' \
  -d '{"walletId":"11111111-1111-4111-8111-111111111111","operationType":"DEPOSIT","amount":100}'
```

В Compose порт приложения опубликован как `8081:8081`. Порт PostgreSQL опубликован как `5433:5432`, чтобы не конфликтовать с локальной базой на `5432`. Для подключения с хоста используй порт `5433`; само приложение внутри Docker-сети использует `postgres:5432`.

### 4. Остановка и данные PostgreSQL

Остановить контейнеры, сохранив данные базы в Docker volume:

```bash
docker compose down
```

Удалить также Docker volume с данными PostgreSQL:

```bash
docker compose down -v
```

**Внимание:** `down -v` удаляет данные контейнерной базы. Скрипты `db/schema.sql` и `db/seed.sql` выполняются автоматически только при первой инициализации пустого каталога данных PostgreSQL. Чтобы повторно применить эти скрипты к существующему тому, нужно отдельно сбросить этот том (данные будут удалены) или выполнить SQL вручную.

**Статус проверки:** я проверил локальное приложение, интеграционные тесты и нагрузку на локальной PostgreSQL. Сам запуск Docker Compose пока не проверен, поэтому после установки Docker следует выполнить приведённые команды и убедиться, что оба контейнера запустились и API отвечает.

## Возможные улучшения для production

- **Retry для временных ошибок БД.** Я бы добавил ограниченное число повторов для подходящих временных ошибок PostgreSQL с задержкой и backoff. Нельзя бездумно повторять операцию, если результат `COMMIT` неизвестен: это может привести к двойному пополнению. Для безопасных повторов HTTP-операций потребуется идемпотентность.
- **Отдельный пакет ошибок.** Сейчас ошибки предметной области объявлены в `repository` и `services`, а handler проверяет ошибки репозитория. Я бы вынес общие ошибки в отдельный пакет, например `apperrors`, чтобы уменьшить связанность между слоями.
- **Точное представление денег.** Сейчас API принимает целые суммы, а баланс читается в `float64`. Перед поддержкой дробных сумм я бы использовал целое число минимальных денежных единиц или decimal-тип, не выполняя денежные вычисления с `float64`.
- **Миграции БД.** Для дальнейшего развития схемы я бы добавил версионируемые миграции.
- **Более длительное нагрузочное тестирование.** Я бы проверил несколько профилей нагрузки и отслеживал задержки, пул соединений, блокировки и использование ресурсов PostgreSQL.

Retry-worker и фоновую повторную обработку операций в текущей версии я не реализовывал.
