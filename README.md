# Wallet API

REST API для работы с балансами кошельков. Проект выполнен на Go с использованием PostgreSQL в рамках тестового задания на Junior Go-разработчика.

## Возможности

- Получение баланса кошелька по UUID.
- Пополнение (`DEPOSIT`) и снятие (`WITHDRAW`) средств.
- Запрет снятия суммы, превышающей доступный баланс.
- Запись успешных операций в таблицу `history`.
- Атомарное изменение баланса и запись истории в одной транзакции PostgreSQL.
- Обработка конкурентных операций с одним кошельком.
- Интеграционные тесты для API, репозитория и конкурентных сценариев.

## Стек

- Go
- PostgreSQL
- `database/sql` и драйвер `pgx`
- `godotenv` для загрузки `config.env`
- Docker Compose для запуска приложения и PostgreSQL

```text
main.go

            └── repository

```

Пакет `db` открывает подключение к PostgreSQL. `main.go` передаёт созданный репозиторий сервисам. HTTP-обработчики не выполняют SQL напрямую.

## Конфигурация

Приложение читает `DATABASE_URL` из переменных окружения; при локальном запуске значения загружаются из `config.env`.

Создайте `config.env` в корне проекта. Пример для локальной PostgreSQL:

```dotenv
DATABASE_URL=postgres://postgres:YOUR_PASSWORD@localhost:5432/testgo?sslmode=disable
```

Замените пользователя, пароль и имя базы на свои значения. Для репозитория используется `config.env.example` с примерными значениями.

### Локальный запуск

1. Запустите локальную PostgreSQL.
2. Создайте базу данных, например `testgo`.
3. Создайте таблицы по схеме из `db/schema.sql` либо используйте уже подготовленную схему.
4. При необходимости заполните `wallet` тестовыми данными из `db/seed.sql`.
5. Создайте и заполните `config.env`.
6. Из корня проекта выполните:

```bash
go mod download
go run .
```

HTTP-сервер слушает порт `8081`.

## REST API

### Получить баланс

```http
GET /api/v1/wallets/{WALLET_UUID}
```

Пример:

```bash
curl -i http://localhost:8081/api/v1/wallets/11111111-1111-4111-8111-111111111111
```

Успешный ответ в текущей реализации — JSON-число, например:

```json
1000
```

### Выполнить операцию

```http
POST /api/v1/wallet
Content-Type: application/json
```

Пример пополнения:

```json
{
  "walletId": "11111111-1111-4111-8111-111111111111",
  "operationType": "DEPOSIT",
  "amount": 100
}
```

Пример запроса через `curl`:

```bash
curl -i -X POST http://localhost:8081/api/v1/wallet \
  -H 'Content-Type: application/json' \
  -d '{"walletId":"11111111-1111-4111-8111-111111111111","operationType":"DEPOSIT","amount":100}'
```

Допустимые значения `operationType`: `DEPOSIT` и `WITHDRAW`. Поле называется `walletId` (написание `valletId` в исходном описании задания трактуется как опечатка). Сейчас API принимает положительную сумму в целых единицах валюты; дробные суммы в запросе не поддерживаются, хотя колонка PostgreSQL имеет тип `numeric(18,2)`.

Успешный `POST` возвращает JSON с данными принятой операции. Баланс отдельно проверяется через `GET`.

### HTTP-статусы

| Код | Значение |
|---|---|
| `200 OK` | Операция выполнена успешно |
| `400 Bad Request` | Некорректный JSON, UUID, сумма или тип операции |
| `404 Not Found` | Кошелёк не найден |
| `409 Conflict` | Недостаточно средств для снятия |
| `405 Method Not Allowed` | Использован неподдерживаемый HTTP-метод |
| `500 Internal Server Error` | Внутренняя ошибка приложения или базы данных |

## Почему для операции используется POST, а не PATCH

### Почему в реализации используется POST, а не PATCH

В техническом задании указан метод `POST /api/v1/wallet`, поэтому в текущей реализации я сохранил заданный контракт.

При этом, если бы я проектировал API самостоятельно, я бы рассмотрел вариант `PATCH /api/v1/wallets/{WALLET_UUID}`, поскольку мы не создаём новый кошелёк, а изменяем баланс существующего. Пополнение увеличивает текущий баланс на указанную сумму, а снятие уменьшает его при условии достаточного остатка.

Запись операций в таблицу `history` — моё собственное дополнение к ТЗ. Я добавил её для сохранения информации о выполненных операциях и обеспечения согласованности данных в рамках одной транзакции. Однако само наличие истории не является причиной выбирать `POST` вместо `PATCH`.

Таким образом, `POST` используется для соблюдения контракта технического задания. При самостоятельном проектировании API я бы отдельно рассмотрел `PATCH` как вариант, лучше соответствующий моей модели изменения существующего ресурса.

## Конкурентность и транзакции

Изменение баланса выполняется атомарными SQL-запросами в PostgreSQL. Для снятия средств запрос содержит условие `balance >= amount`, чтобы конкурентные операции не могли увести баланс в минус.

Изменение баланса и вставка записи в `history` выполняются в одной транзакции. Если запись истории не удаётся, транзакция не должна фиксировать изменение баланса. Отдельный Go `sync.Mutex` не используется: синхронизацию конкурентных обновлений одной строки выполняет PostgreSQL.

## Тестирование

Тесты в `tests/` — интеграционные и требуют доступной PostgreSQL со схемой, соответствующей проекту, и корректного `config.env`. Тестовые кошельки создаются с отдельными UUID и очищаются после выполнения.

Запустить все тесты:

```bash
go test ./... -count=1
```

Проверить гонки данных в Go:

```bash
go test -race ./tests -count=1
```

Посмотреть покрытие основных пакетов:

```bash
go test \
  -coverpkg=./handler,./services,./repository,./dbmodel \
  -coverprofile=coverage.out \
  ./tests -count=1

go tool cover -func=coverage.out
```

Зафиксированный результат во время разработки — **88,5% покрытия операторов** в пакетах `handler`, `services`, `repository` и `dbmodel`.

**Примечание об использовании ИИ:** интеграционные тесты были сгенерированы с помощью ИИ, после чего автор запускал их и проверял результаты на своей локальной PostgreSQL. Этот факт указан явно; результаты тестов относятся к сценариям, которые они действительно проверяют.

## Нагрузочное тестирование

Нагрузку на локальный HTTP-сервер генерировали утилитой [`hey`](https://github.com/rakyll/hey). Тест направлял конкурентные `POST`-запросы с пополнением одного кошелька.

Зафиксированный успешный прогон:

- длительность: `10.0841` секунды;
- фактическая пропускная способность: `1090.53 RPS`;
- успешные ответы: `10 997` со статусом `200`;
- ответы `5xx`: `0`;
- среднее время ответа: около `45.4 ms`;
- p50: `45.9 ms`;
- p99: `86.3 ms`.

После прогона проверка PostgreSQL показала баланс `10997.00`, `10997` успешных записей в истории и сумму истории `10997.00`. Таким образом, в этом запуске число успешных пополнений совпало с балансом и историей.

Это результат локального окружения разработчика, а не гарантия производительности на другом оборудовании или в production. Один короткий прогон не заменяет длительный нагрузочный тест и наблюдение за ресурсами PostgreSQL.

## Docker Compose

В проекте предусмотрена конфигурация Dockerfile и Compose для запуска приложения вместе с PostgreSQL. Для Compose в `config.env` нужны переменные контейнерной БД, например:

```dotenv
POSTGRES_USER=wallet_user
POSTGRES_PASSWORD=wallet_pass_123
POSTGRES_DB=testgo
DATABASE_URL_DOCKER=postgres://wallet_user:wallet_pass_123@postgres:5432/testgo?sslmode=disable
```

`DATABASE_URL` для локального запуска и `DATABASE_URL_DOCKER` для приложения внутри Compose используют разные адреса: внутри Docker-сети PostgreSQL доступна по имени сервиса `postgres`, а не через `localhost`.

Запуск:

```bash
docker compose --env-file config.env up --build
```

В предложенной конфигурации PostgreSQL публикует порт `5433` на хосте, чтобы не конфликтовать с локальной БД на `5432`; приложение доступно на `http://localhost:8081`.

**Статус проверки:** локальные Go-тесты, `go vet` и нагрузочный прогон выполнены. Запуск Docker Compose в этой среде не выполнялся, поэтому контейнерную конфигурацию нужно проверить на машине с установленным Docker перед сдачей задания.

## Возможные улучшения для production

- **Retry для временных ошибок БД.** Добавить ограниченное число повторов только для подходящих временных ошибок PostgreSQL, с задержкой и backoff. Нельзя бездумно повторять операцию, если результат `COMMIT` неизвестен: это может привести к двойному пополнению. Для HTTP-операций нужен механизм идемпотентности.
- **Выделить ошибки в отдельный пакет.** Сейчас ошибки предметной области объявлены в `repository` и `services`, а handler знает о типах ошибок репозитория. Их можно вынести, например, в `apperrors`/`domain/errors`, чтобы уменьшить связанность слоёв.
- **Точное представление денег.** Сейчас API принимает целые суммы, а баланс читается в `float64`. Перед поддержкой дробных значений стоит использовать целое число минимальных денежных единиц либо decimal-тип, не выполняя денежную арифметику с `float64`.
- **Миграции схемы.** Для развития структуры БД добавить инструмент миграций, чтобы изменения схемы были версионированы и воспроизводимы.
- **Расширенный мониторинг нагрузки.** Повторять нагрузочные тесты с разной длительностью и отслеживать пул соединений, блокировки, задержки и использование ресурсов PostgreSQL.

Retry-worker и фоновая повторная обработка операций в текущей версии не реализованы.
